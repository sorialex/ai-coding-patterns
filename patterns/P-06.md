# P-06 — Background Job System Reimplemented From Scratch

## Example

```python
# api/module_a.py
_jobs = {}

@router.post("/process")
def start_process(payload: JobRequest):
    job_id = uuid.uuid4().hex[:8]
    _jobs[job_id] = {"status": "pending"}
    thread = threading.Thread(target=_run_job, args=(job_id, payload), daemon=True)
    thread.start()
    return {"job_id": job_id}

@router.get("/process/{job_id}")
def poll_process(job_id: str):
    return _jobs.get(job_id, {"status": "not_found"})
```

The same structure — module-level dict, `uuid4().hex[:8]`, daemon thread,
POST-to-start + GET-to-poll — appears across multiple modules.
Each frontend module has a matching `setTimeout`-based recursive poller.

## Why it happens

The agent has no cross-session memory. Each new async endpoint is treated
as a fresh, isolated task. The agent has a strong prior for "HTTP polling
is the async pattern" and executes it fluently from the same internal
template each time — without recognizing it has already been implemented
elsewhere in the project.

The identical `hex[:8]` job ID scheme across all implementations is a
reliable indicator: the agent is reproducing from pattern-match, not
reusing existing code.

## Why it's a problem

- N identical implementations to maintain; a bug fix in one does not
  propagate to the others.
- In-memory job dicts grow without bound — no TTL, no cap, no eviction.
  The only cleanup path is a server restart.
- No shared abstraction to improve, replace, or test in isolation.
- Frontend pollers are also duplicated, compounding the maintenance cost.

## Measure

```
Before implementing any async endpoint with a polling mechanism, search
the codebase for existing job queue patterns (look for: module-level dicts
used as job stores, uuid job IDs, daemon threads, POST/GET polling pairs).
If found, extract to a shared job_queue.py module before adding new
endpoints. Never implement a new job store per module.
```
