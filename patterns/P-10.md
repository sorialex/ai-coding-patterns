# P-10: Build system threshold

## The pattern

The agent solves build-related problems incrementally and locally. Each new requirement
gets patched into the nearest available mechanism — a script entry, a one-liner, a manual
step documented in a comment. The agent never evaluates whether the accumulated complexity
has crossed a threshold where an ad-hoc collection of steps should become an explicit,
managed build system.

## Why it happens

The agent reasons about the immediate task, not about the trajectory of the project.
When a build concern first appears — compile the sources, minify an asset — the simplest
fix is correct. When a second, unrelated concern appears, the agent applies the same
logic: patch it in. There is no trigger that causes the agent to step back and ask
whether the collection of patches now constitutes an implicit build pipeline that would
be better expressed explicitly.

The result is a project where the build process is distributed across package scripts,
Makefiles, README steps, CI configuration, and individual contributor habits — none of
which is authoritative, and any of which can diverge from the others silently.

## Why it's a problem

Distributed build logic is invisible to automated checking. When steps live in different
places, no single point of failure exists — so no single point of validation exists either.
Environments diverge (local vs CI vs production) because different contexts execute
different subsets of the implicit pipeline. New contributors reproduce the project
incorrectly because the real build process is not where they look. The agent, on
subsequent tasks, also reproduces it incorrectly for the same reason.

The cost compounds: each new contributor or deployment environment that onboards against
a broken or incomplete build description widens the divergence. Fixing it later requires
archaeological reconstruction of what the intended pipeline was.

## Threshold signals

Any one of the following should trigger explicit build system evaluation:

- **Second build language or runtime.** The project now contains source artifacts that
  require different toolchains to process. A single toolchain can manage its own outputs;
  two cannot manage each other's without coordination.

- **Artifact placement outside the source tree.** A file must exist in a location other
  than where it is authored — compiled, copied, generated, or bundled. The relationship
  between source and output is now a build concern, not a file concern.

- **Environment-specific behavior.** The project behaves differently depending on which
  steps the operator ran before executing it. This is a symptom that the build process is
  not fully encoded anywhere.

- **More than two script entries for build-related tasks.** Script entries that invoke,
  orchestrate, or depend on each other are a build system expressed in the wrong language.

- **A manual step in the documentation.** Any README section that says "before running,
  make sure to..." is a build step that escaped the build system.

## Correct behavior

When a threshold signal appears, the agent should surface it explicitly before solving
the immediate problem:

> "This task introduces a second build concern. The current approach handles [existing
> concern] via [mechanism]. Adding [new concern] as another local patch will make the
> build process harder to reproduce and maintain. Before proceeding, it's worth deciding
> whether to consolidate into a build tool (Make, Task, a dedicated script) that owns
> all build steps in one place."

The agent should not proceed with the patch if doing so would deepen an already-fragmented
build process. Proposing the consolidation and implementing it is within scope of the task.

## What this is not

This pattern is not about choosing the correct build tool, or about the merits of any
particular approach. It is about the agent's failure to recognize that a decision point
exists — and its default of always taking the incremental path regardless of whether
the incremental path is still appropriate.

## Measure

```
When adding any build-related task (compilation, asset pipeline, code generation,
deployment step), check whether any threshold signal is now present in the project:
a second language or runtime, artifact placement outside the source tree, environment-
specific behaviour, more than two build script entries, or a manual step in the docs.
If any signal is present, do not patch in the new step — consolidate all build steps
into a single authoritative mechanism first, then add the new step there.
```
