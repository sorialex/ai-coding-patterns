# P-12: Async loading state stored in DOM, not in application state

## Example

```js
// A multi-step form. Step 2 has an async submit button.

async function submitForm() {
    const btn = document.getElementById("submitBtn");
    btn.disabled = true;
    btn.innerHTML = "Submitting...";   // written directly to DOM, not to appState

    try {
        await api.submit(formState.data);
        showStep(3);  // step 2 panel hidden — btn still reads "Submitting..." in DOM
        // success path never resets btn
    } catch (e) {
        btn.disabled = false;          // error path resets correctly
        btn.innerHTML = "Submit";
        alert(e.message);
    }
}

// Called on every step transition, including navigating back to step 2
function showStep(n) {
    formState.step = n;
    document.querySelectorAll(".step-panel").forEach((p, i) =>
        p.classList.toggle("hidden", i + 1 !== n)
    );
    // btn appearance is not refreshed — DOM retains "Submitting..." if step 2 is re-shown
}

function updateSubmitBtn() {
    const btn = document.getElementById("submitBtn");
    const canSubmit = formState.data.trim().length > 0;
    btn.disabled = !canSubmit;
    btn.innerHTML = "Submit";          // always resets to ready state — but never called from showStep
}
```

When the user navigates away and back to step 2 — via the step indicator, an external
entry point, or `initializeView()` — `showStep(2)` re-displays the panel but does not call
`updateSubmitBtn()`. The button retains "Submitting..." indefinitely.

## Why it happens

The agent reaches for the most direct path to show a loading indicator: grab the DOM
element in scope and write to it. This works for the immediate interaction. But the
in-flight status is stored in the DOM, not in `formState`, making it invisible to every
function that derives UI appearance from application state.

The error path correctly resets the button because it runs in the same async frame. The
success path doesn't, because the mental model is "the panel is hidden now, so the button
doesn't matter." That holds until any code re-shows the panel without going through the
original success handler.

The rendering function (`updateSubmitBtn`) exists and is correct, but it is only wired to
the path that enters step 2 from step 1. Any other path that calls `showStep(2)` directly
bypasses it.

## Why it's a problem

The loading indicator becomes permanently stuck for any user who re-enters the step. The
application state says "ready"; the DOM says "Submitting..." — an invisible divergence
that only surfaces on second use, not during the initial development and testing of the
happy path.

It also creates a silent double-submission risk. If the stuck `disabled` state is lifted
by a subsequent state change, the user can trigger a second operation while the first is
still in flight, because application state contains no lock.

## Measure

```
For any async operation that changes a UI element's appearance (spinner,
disabled state, progress text), store the in-flight status in application
state (e.g. state.submitting = true/false) before touching the DOM.
The rendering function must be the single source of truth: derive all
element appearance from state, and call it from every code path that makes
the containing panel or step visible — not just from the primary entry path.
Never use direct DOM mutation to represent transient operation state. If the
DOM element can be hidden and re-shown by any navigation path, its visual
state must survive that round-trip through the application state layer.
```
