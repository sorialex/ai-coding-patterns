# P-07: Silent schema migration

## Example

```python
def migrate(self):
    try:
        cursor.execute("ALTER TABLE items ADD COLUMN field_a TEXT")
    except:
        pass

    try:
        cursor.execute("ALTER TABLE items ADD COLUMN field_b TEXT")
    except:
        pass

    # Repeated for every column addition, no logging, no versioning
```

Every `ALTER TABLE` call is wrapped in a bare `except: pass`.
No logging, no error discrimination, no migration versioning.

## Why it happens

`try/except: pass` is the simplest way to make `ALTER TABLE` idempotent —
it silently handles "column already exists" without failing on a running
database. The agent applies this idiom universally to every schema change
without distinguishing expected failures (column exists) from unexpected
ones (disk full, permissions error, DB corruption).

## Why it's a problem

All failure types produce the same silence:
- Column already exists → pass → (intended)
- Disk full → pass →
- DB file corrupted → pass →
- Permission denied → pass →

A failed migration is indistinguishable from a successful no-op.
Schema state becomes unknowable over time — there is no record of
which columns were successfully added and which silently failed.

## Measure

```
Never use bare except: pass on schema operations. Catch only the
specific exception for "column already exists" (e.g. sqlite3.OperationalError
with "duplicate column" in the message) and log everything else as an error.
For projects with more than 3 schema migrations, introduce a schema_version
table to track applied migrations explicitly.
```
