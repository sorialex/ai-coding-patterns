# P-02: Hardcoded strings without i18n system

## Example

```jsx
// Strings written directly into markup
<h1>Welcome back</h1>
<p>Your order has been confirmed</p>
<button>Cancel</button>
```

## Why it happens

The AI optimizes for the immediate task — making the UI work — and
treats text as a detail. It does not check for an existing i18n
setup unless explicitly instructed. When i18n is added later, it
has no prior context to know which strings it generated.

## Why it's a problem

Retrofitting i18n requires traversing every file in the project.
With an AI agent this multiplies token cost and introduces
inconsistency risk: missed strings, duplicate keys, or keys that
don't follow the established naming convention.

## Measure

```
If the project has an i18n setup (check for /locales, /i18n folders
or libraries like i18next, react-intl), every user-facing string must
use the translation system from the first commit. Never hardcode
visible strings in JSX or templates. Retrofitting i18n across an
existing codebase is expensive and error-prone.
```
